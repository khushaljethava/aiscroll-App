> Generated by `/multi-plan` (Claude-only fallback — `codeagent-wrapper` not installed).

## TL;DR — Most-likely root causes (ranked)

The polling pipeline is wired correctly end-to-end. If the user perceives "no updates," it is almost certainly **one** of the following — listed by likelihood given the existing diagnostic plans in `.claude/plan/news-404-rootcause.md`:

1. **`ADMIN_API_URL` misconfigured / stale dart-define** *(very high)* — `String.fromEnvironment` is **compile-time**, so a forgotten `flutter clean` after changing the URL keeps the old (or empty) value baked into the binary. When empty, `refreshFromNetwork` short-circuits with `_lastError = 'ADMIN_API_URL not configured; staying on cached data.'` and the periodic timer becomes a no-op.
2. **Server returns 401/404/308** — auth pipeline (`authedDioFactoryProvider` → `AuthService.getValidToken`) fails silently when Firebase / App Check isn't set up; `_lastError` is set but the `_StaleBanner` only renders when `lastSyncedAt > 24 h` AND `lastError != null` (`news_screen.dart:186-188`), so the user sees no signal that polling is failing.
3. **Server has no new articles** — admin's news ingestion cron isn't producing fresh items; refresh succeeds but the list is byte-identical, nothing visibly changes.
4. **PageView "stuck" perception** — periodic refresh prepends new articles (server orders by `isPinned desc, publishedAt desc`), but the `PageController` keeps the user on their current `index`. A user on page 5 stays on page 5, which is now an *older* article than what they were reading. They scroll forward, see older content, conclude "nothing's updating." Pull-to-refresh (`_onRefresh` at `news_screen.dart:67-73`) explicitly jumps to page 0; periodic refresh does **not**.
5. **First periodic tick is at +2 min** — `Timer.periodic` does not fire at `t=0`. If the user hot-restarts and watches for 90 s, the only network call is the initial cold-start refresh kicked from `app.dart:106`. They may misread this as "polling never happens."

The plan below: (A) instrument so the user can self-diagnose in 60 s, then (B) harden the failure-surfacing UX so the same misperception can't recur silently, and (C) close the PageView perception gap.

## Where the silent failures live

### S1 — `_lastError` is set but never surfaced to UI
`news_screen.dart:186-188`:
```dart
final stale = last == null ||
    DateTime.now().difference(last) > const Duration(hours: 24);
if (!stale || state.lastError == null) return const SizedBox.shrink();
```
The stale banner requires **both** `lastError != null` AND (no cached data OR cache > 24 h). A successful initial refresh followed by 12 hours of failing periodic polls renders **zero** UI signal. Polling is broken; user can't tell.

### S2 — `_safeRefresh` swallows exceptions in release builds
`periodic_sync_scheduler.dart:71-87`:
```dart
} catch (e) {
  debugPrint('PeriodicSyncScheduler[$label]: $source threw $e');
}
```
`debugPrint` is a no-op in `--release`. `_refresh()` is supposed to be non-throwing (`refresh` already does `try/catch` internally), but if it somehow throws, nothing reaches state. Defensive but invisible.

### S3 — Periodic timer success is invisible
The user can't tell the difference between "polled and no new articles" vs "didn't poll." No timestamp shown anywhere except the (gated) stale banner.

### S4 — PageView keeps stale index after periodic prepend
`news_screen.dart:67-73`:
```dart
Future<void> _onRefresh() async {
  ...
  await ref.read(newsProvider.notifier).refresh();
  if (_pageController.hasClients) {
    _pageController.jumpToPage(0);   // ← only the manual path resets index
  }
}
```
The periodic path goes through `scheduler._safeRefresh('periodic') → refresh()` directly, never touching the controller. Result: user on page index 5 stays on index 5 even though indices have shifted.

## Technical Solution

### Phase A — Diagnose (do this first; takes ~60 s)

#### A1. Print the composed URL + auth state on every refresh
`news_service.dart` already has `debugPrint('NewsService: fetching $_baseUrl/api/news?limit=$_defaultLimit');` at line 105 — keep it. Add one more print right after the `if (!isAdminConfigured)` early-return so the empty-URL case is also visible:

```dart
// news_service.dart, around line 96
if (!isAdminConfigured) {
  _lastError = 'ADMIN_API_URL not configured; staying on cached data.';
  debugPrint('NewsService: ADMIN_API_URL is empty — '
             'rebuild with --dart-define=ADMIN_API_URL=<host>');
  return false;
}
```

#### A2. Print scheduler tick events
`periodic_sync_scheduler.dart` already logs skip + throw. Add one log on entry so the user can confirm the timer is actually firing:

```dart
// periodic_sync_scheduler.dart, in _safeRefresh, after the in-flight guard
_inFlight = true;
debugPrint('PeriodicSyncScheduler[$label]: $source tick @ '
           '${DateTime.now().toIso8601String()}');
try {
  await _refresh();
}
```

#### A3. Print article-id fingerprint per refresh
So the user can tell if the server is sending new content.

```dart
// news_service.dart, after _articles = decodedArticles;
debugPrint('NewsService: refreshed ${decodedArticles.length} articles, '
           'top id=${decodedArticles.isEmpty ? "<empty>" : decodedArticles.first.id} '
           'top published=${decodedArticles.isEmpty ? "" : decodedArticles.first.publishedAt.toIso8601String()}');
```

#### A4. Decision tree
After hot-restart and ~3 minutes of foreground use, the user reads logcat / Flutter DevTools logs:

| Log pattern | Diagnosis | Fix |
|---|---|---|
| `ADMIN_API_URL is empty` | Misconfigured dart-define | `flutter clean && flutter run --dart-define=ADMIN_API_URL=<host>` |
| `fetching https://wrong-host/api/news` | Wrong host baked in | Same — use the production alias from Vercel |
| `News fetch failed: HTTP 401` (in stale banner) | JWT/App Check misconfig | See `.claude/plan/news-404-rootcause.md` §5 |
| `News fetch failed: HTTP 404` | Wrong host or stale deployment | Same plan, §3 D2/D3 |
| `Network error: …` | Device offline / firewall | Network sanity check |
| `periodic tick @ …` appears every 2 min, fingerprint never changes | Server has no new content | Verify admin's news ingestion cron is running |
| No `periodic tick` log ever appears, even after 3 min foregrounded | Scheduler not started | Check `scheduler.start()` call path in `app.dart:107` ran |
| `periodic tick` appears, fingerprint changes, but user still sees old article | PageView perception (Phase C) | See Phase C below |

### Phase B — Surface failures continuously, not just after 24 h

#### B1. Loosen the stale-banner gate
`news_screen.dart:178-223` — change the gate so users see polling failures within minutes, not days:

```dart
// Before
final stale = last == null ||
    DateTime.now().difference(last) > const Duration(hours: 24);
if (!stale || state.lastError == null) return const SizedBox.shrink();

// After
if (state.lastError == null) return const SizedBox.shrink();
final last = state.lastSyncedAt;
final ageMinutes = last == null ? null : DateTime.now().difference(last).inMinutes;
final severe = last == null || ageMinutes! > 30;   // 30 min = "this matters"
// Render the banner whenever there's an error. Tone it down (subtle yellow)
// when cache is fresh; escalate (red border) when cache is severely stale.
```

Rationale: the current 24-hour threshold was designed for the *cold-start with no internet* case. It misses every "I had connectivity, then lost it for an hour" case in between.

#### B2. Show a tiny "last updated Xm ago" affordance
Either as a chip on the category rail or a one-line subtitle under the first article. This kills the "is it polling?" question outright.

```dart
// news_screen.dart, somewhere in the build (e.g. inside _StaleBanner or a new
// _FreshnessChip widget rendered above the category rail)
Text(
  state.lastSyncedAt == null
      ? 'Never synced'
      : 'Updated ${_relativeTime(state.lastSyncedAt!)}',
  style: tt.labelSmall?.copyWith(color: cs.onSurfaceVariant),
);
```

`_relativeTime` already exists at `news_screen.dart:1089-1095` — reuse it.

#### B3. Promote `_safeRefresh` errors into state
Currently the scheduler swallows refresh exceptions. The `refresh()` method *should* never throw, but if it does, the state's `lastError` won't capture it. Belt-and-braces:

```dart
// periodic_sync_scheduler.dart
} catch (e) {
  debugPrint('PeriodicSyncScheduler[$label]: $source threw $e');
  // Don't try to reach back into state — keep the scheduler decoupled.
  // This branch should be unreachable; the print is the entire signal.
}
```
No code change needed here unless we add a callback parameter for "scheduler-level error" — out of scope unless the user wants it.

### Phase C — Fix the PageView "stuck" perception

When periodic refresh prepends new articles, give the user an explicit affordance instead of silently shifting indices.

#### C1. Detect new articles between refreshes
Track the previous "top article id" in the notifier; emit a "new stories available" flag in state.

```dart
// news_provider.dart — add field
class NewsState {
  ...
  final int unseenNewCount;   // 0 means caught up
  ...
}

// in NewsNotifier.refresh()
final prevTopId = state.articles.isEmpty ? null : state.articles.first.id;
await _service.refreshFromNetwork();
final newArticles = _service.articles;
int unseen = 0;
if (prevTopId != null) {
  for (final a in newArticles) {
    if (a.id == prevTopId) break;
    unseen++;
  }
}
state = state.copyWith(
  articles: newArticles,
  ...
  unseenNewCount: state.unseenNewCount + unseen,
);
```

(Reset `unseenNewCount` to 0 inside `_onRefresh` and when user `jumpToPage(0)`.)

#### C2. Render a "↑ N new stories" pill on top of the feed
```dart
// news_screen.dart, in build, after _CategoryRail
if (state.unseenNewCount > 0)
  _NewStoriesPill(
    count: state.unseenNewCount,
    onTap: () {
      _pageController.jumpToPage(0);
      ref.read(newsProvider.notifier).markUnseenSeen();
    },
  ),
```

#### C3. (Optional) Stick to page 0 if the user is already there
If `_pageController.page == 0` when refresh completes, *don't* require the tap — call `jumpToPage(0)` automatically so the new top article is visible. Preserves user position when they're mid-feed.

```dart
// news_provider.dart — expose a side-effect callback OR
// news_screen.dart — react to a state change in didChangeDependencies / ref.listen
ref.listen<NewsState>(newsProvider, (prev, next) {
  if (prev?.articles.firstOrNull?.id != next.articles.firstOrNull?.id) {
    if (_pageController.hasClients && _pageController.page == 0) {
      _pageController.jumpToPage(0);
    }
  }
});
```

## Pseudo-code summary

```dart
// news_provider.dart (delta)
class NewsState {
  ...
  final int unseenNewCount;
  ...
}

class NewsNotifier extends StateNotifier<NewsState> {
  Future<void> refresh() async {
    final prevTopId = state.articles.isEmpty ? null : state.articles.first.id;
    state = state.copyWith(refreshing: true);
    await _service.refreshFromNetwork();
    final newArticles = _service.articles;
    final unseen = _countUnseen(prevTopId, newArticles);
    state = state.copyWith(
      articles: newArticles,
      categories: _service.categories,
      lastSyncedAt: _service.lastSyncedAt,
      lastError: _service.lastError,
      unseenNewCount: state.unseenNewCount + unseen,
      refreshing: false,
    );
  }

  void markUnseenSeen() => state = state.copyWith(unseenNewCount: 0);
}

// news_screen.dart (delta)
ref.listen<NewsState>(newsProvider, (prev, next) {
  final wasAtTop = _pageController.hasClients && (_pageController.page ?? 0) < 0.5;
  if (wasAtTop && prev?.articles.firstOrNull?.id != next.articles.firstOrNull?.id) {
    _pageController.jumpToPage(0);
    ref.read(newsProvider.notifier).markUnseenSeen();
  }
});

return Column(children: [
  _FreshnessChip(state: state),
  if (state.unseenNewCount > 0) _NewStoriesPill(count: state.unseenNewCount, onTap: () {
    _pageController.jumpToPage(0);
    ref.read(newsProvider.notifier).markUnseenSeen();
  }),
  _StaleBanner(state: state),       // gate loosened
  _CategoryRail(...),
  Expanded(child: _FeedBody(...)),
]);
```

## Risks and Mitigation

| Risk | Mitigation |
|---|---|
| `debugPrint` floods logcat in production | All Phase A logs are diagnostic; gate with `if (kDebugMode)` if needed before shipping. The existing line 105 print isn't gated, so consistency-wise it's fine to leave. |
| Loosening the stale-banner gate produces banner-spam on every transient failure | Show a *subtle* tone (info-blue, not warning-red) for fresh-cache + error; escalate only when stale > 30 min. |
| `unseenNewCount` over-counts when admin reorders pinned/unpinned articles | Compare by `id` not by position; "unseen" is purely "appeared above what was previously top". This handles re-pinning conservatively (a re-pinned old article *will* count as "new", which is acceptable — it's a rare event and arguably correct UX). |
| `ref.listen` auto-jump steals user's swipe in flight | Guard with `_pageController.position.isScrollingNotifier.value == false` before jumping, OR only auto-jump within a 200 ms debounce after refresh completion. |
| Adding new state field breaks existing tests | `NewsState` constructor has named params; default `unseenNewCount: 0`. Existing call sites unaffected. |
| User's actual problem is none of the above | Phase A logs will reveal the truth in 60 s. We ship Phase A first as a self-contained diagnosis PR; Phases B & C only land after the symptom is confirmed. |
| Periodic refresh runs while admin is briefly down → false-positive "polling broken" banner | The B1 banner shows error text from `_lastError` only; one transient 503 sets it but the next successful tick clears it. Showing the truth is better than hiding it for 24 h. |
