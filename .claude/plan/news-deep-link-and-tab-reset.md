# Implementation Plan: Notification Deep-Link "Article Not Available" + News Tab Doesn't Show Latest

> Generated by `/multi-plan` (Claude-only fallback — `codeagent-wrapper` not installed).
> Two bugs reported together; both are about the news feed entry surface.

## Task Type
- [x] **Backend** (auth race, fetchById error reporting, retry semantics)
- [x] **Frontend** (NewsScreen tab-reselect handler, NewsDetailScreen retry UI)
- [x] **Lifecycle / routing** (`_MainShell` re-tap signal, `app.dart` boot-order tightening)

## Problem 1 — "Article no longer available" on notification tap

### Reproduction path

1. User receives FCM push (foreground / background / terminated all in scope).
2. Tap → `news_push_service.dart:65-77` extracts `m.data['articleId']` and calls `goToNewsArticle(id)`.
3. `core/router/deep_link.dart:19-30` either dispatches now or queues until `markRouterReady()` fires.
4. `app_router.dart:227-239` mounts `NewsDetailScreen(articleId, initialArticle: state.extra)` — **`extra` is null** for FCM-driven taps; it's only set when navigating from the in-app feed (`news_screen.dart:123`).
5. `news_detail_screen.dart:53-59` checks the in-memory feed cache first (`newsArticleByIdProvider`), then falls back to `newsArticleFetchProvider(id)` → `NewsService.fetchById(id)`.
6. `news_service.dart:197-216` GETs `<base>/api/news/<id>` and **collapses every non-200 response and every exception to `null`**. Provider's `data: null` branch → `_notFoundScaffold()` → "Article no longer available."

### Root causes (ranked)

#### R1.1 — Cold-start auth race *(most likely)*
`app.dart:62-119` postFrameCallback:
```
hydrate (cache) → load user/quests → authService.getValidToken (UNAWAITED) → telemetry → contentNotifier.refresh → newsNotifier.refresh → markRouterReady() → newsPushService.init()
```
`getValidToken` is called with `// ignore: discarded_futures` (line 83) — it is **not awaited**. App Check + token round-trip can take 1-3 s. Meanwhile `markRouterReady()` runs immediately after, the queued deep-link fires, NewsDetailScreen mounts, `fetchById` is invoked, the request goes out without `Authorization` header (or with a still-pending one), admin returns 401, `fetchById` returns null, "Article no longer available."

This is consistent with what we just observed in the previous session: admin returns `401 Unauthorized` to unauth'd `GET /api/news/<id>` (we curl-tested both `/api/news/some-fake-id` and a real id — both 401).

#### R1.2 — Every failure collapses to "no longer available"
`news_service.dart:205, 213` returns `null` for **all** of: 401, 404, 500, network down, server returned non-JSON, body shape wrong. The UI cannot tell the user *why* the fetch failed, so even a transient connectivity blip looks like "article gone forever."

#### R1.3 — Article id mismatch FCM ↔ admin
The FCM payload's `articleId` might differ from what the admin DB serves at `/api/news/<id>`. We saw evidence in last session's log of a possibly-truncated id (`hugging-face-transformers-v5-4-adds-mistral-4-paddlepaddle-support-and-lightweig` ends mid-word). If the cron-publishing pipeline truncates slugs at one length and the home-feed uses another, deep-link by id breaks even when auth is healthy.

#### R1.4 — `newsArticleFetchProvider` is `autoDispose.family`
`news_provider.dart:184-196`. Once the screen pops, the cache is dropped. A second visit re-fetches. Not the bug, but compounds R1.2: a user retrying the notification tap pays full latency every time.

#### R1.5 — `getInitialMessage()` may fire before token is ready on cold start
Same race as R1.1 but specifically for the *terminated* path. `news_push_service.init()` is the **last** thing in the postFrame callback and `getInitialMessage()` is awaited inline; whatever it returns goes into `goToNewsArticle` immediately.

### Open question (flag for user)

**Does the admin send any of the article fields in the FCM `data` payload?** If yes (or it's cheap to add), we can populate `initialArticle` on the deep-link path and skip the network fetch entirely — the screen renders instantly, no auth race possible. Currently the FCM data only contains `articleId`, `title`, `body`. Worth checking the admin's `news.pipeline` push step.

## Problem 2 — News tab shows "current one only", not latest

### Reproduction path

1. User opens app → cold-start refresh fills feed → user is at PageView index 0.
2. User swipes down through several stories — now at index 5.
3. User taps a different bottom-nav tab (e.g. Profile), comes back to News tab.
4. `_MainShell.onDestinationSelected` (`app_router.dart:107-110`):
   ```dart
   onDestinationSelected: (index) => navigationShell.goBranch(
     index,
     initialLocation: index == navigationShell.currentIndex,
   ),
   ```
   `initialLocation: true` is passed only when re-tapping the **current** tab. For tab-switching to a *different* branch, `initialLocation: false` — the branch's saved location is restored.
5. `StatefulShellRoute.indexedStack` keeps each branch's widget tree alive. NewsScreen's `_pageController` is a state field that survives across tab switches.
6. User comes back → still at index 5 → sees "the article they were last on", not "the latest."

### Root cause

**`_pageController` is never reset when the user re-enters the News tab from another tab.** No code path connects "user returns to News" to "scroll PageView back to top" or "refresh feed."

Two distinct UX expectations get conflated by this:
- **A. "Show me the latest"** — user wants to see new articles at the top
- **B. "Resume where I was"** — user wants to keep their reading position

Per the bug report, the user expects A. The current implementation does B implicitly (because `_pageController` persists). There's no toggle for the user.

### Edge cases

- User taps News tab while reading a `NewsDetailScreen` (inside the News branch). With `initialLocation: true` on re-tap, the `goBranch` already pops detail back to NewsScreen root — but the PageView is still at index 5.
- User opens the app for the first time today (cold start). They expect "latest." Today they actually get it because cold-start refresh fires + PageController initialises at 0.
- User tap-tap-taps News tab. We don't want every tap to trigger a network refresh — wasteful.

## Technical Solution

### Fix Problem 1 (deep-link notification → article)

#### Approach 1 — Distinguish error types in `fetchById` + retry on auth failure (chosen)
Replace the current "everything → null" with a typed result so the UI can:
- show a spinner + retry button on transient errors,
- show "article not found" only for genuine 404s,
- automatically retry once after a short delay if the first attempt got 401 (covers the cold-start race).

#### Approach 2 — Await JWT readiness before draining queued deep-links (chosen, complementary)
In `app.dart`, await `authService.getValidToken(...)` **before** `markRouterReady()` and `newsPushService.init()`. This eliminates R1.1 / R1.5 entirely — by the time NewsDetailScreen mounts, the JWT is in the cache and the Dio interceptor will attach it on the first request.

Cost: cold start blocks for one App Check round-trip (~1-3 s) before the queued deep-link fires. We're already showing the splash/cache-hydrated UI by then so the visible delay is just "tap notification, see splash content for an extra 1-2 s, then jump to article" — which is what the user expects anyway.

#### Approach 3 — Embed full article snapshot in FCM payload (rejected for now, future)
Server-side change. Pushes payload size up (FCM data is capped at 4 KB). Worth doing for hot articles but out of scope here. If the user confirms server can include a JSON snapshot under `data['article']`, NewsDetailScreen reads it as a synchronous fast path (zero network).

### Fix Problem 2 (News tab re-tap shows latest)

#### Approach 1 — Tab re-tap → reset + refresh-if-stale (chosen)
Wire a Riverpod signal that increments when the News tab is tapped while already selected. NewsScreen `ref.listen`s on it and runs:
```
1. _pageController.jumpToPage(0)
2. scheduler.refreshIfStale()  // reuses 30 s threshold
3. markUnseenSeen()             // clear "↑ N new stories" pill
```
The 30 s threshold (already configured in `news_provider.dart:74`) prevents tap-spam from flooding the admin.

This is the "Twitter top-tap" UX. Familiar, predictable, cheap.

#### Approach 2 — Reset on every tab switch into News (rejected)
Wipes user's reading position even on accidental tab switches. Annoying.

#### Approach 3 — Auto-jump-to-top whenever cache is older than X (rejected)
Heuristic, surprises users mid-read. Phase C of the previous plan already auto-jumps when the user is **at index 0** — that's the right behaviour. We don't want to extend it to "anywhere in feed."

## Implementation Steps

### Phase A — Tighten boot order so deep-links wait for auth

#### A1. Await JWT prime before draining deep-links
**File:** `lib/app.dart`, postFrameCallback

```dart
// Step 2b becomes awaited.
final user = ref.read(userProvider);
final token = await ref
    .read(authServiceProvider)
    .getValidToken(guestId: user.id);

// Step 7 (markRouterReady) and Step 8 (newsPushService.init) MUST run after.
markRouterReady();
// ignore: unawaited_futures
ref.read(newsPushServiceProvider).init();
```

Risks:
- If `getValidToken` hangs (e.g. App Check unreachable), the deep-link never fires.
  → **Mitigation:** wrap with `.timeout(const Duration(seconds: 4), onTimeout: () => null)`. Even with a stale token in the cache, the screen flow proceeds.
- If `getValidToken` fails (returns null), the deep-link still fires — Dio interceptor will retry-on-401 once, and `fetchById`'s typed error path (Phase B) gives the user a Retry button.

#### A2. Do not block content refresh on auth
The existing pattern of running `contentNotifier.refresh()` and `newsNotifier.refresh()` *unawaited* (lines 99, 106) stays — those are best-effort and the cache covers their absence. Only the **deep-link drain** waits.

### Phase B — Typed errors in `fetchById` + retry-on-401 + retryable UI

#### B1. Replace `Future<NewsArticle?>` with a sealed result
**File:** `lib/data/remote/news_service.dart`

```dart
sealed class FetchByIdResult {
  const FetchByIdResult();
}

class FetchByIdSuccess extends FetchByIdResult {
  const FetchByIdSuccess(this.article);
  final NewsArticle article;
}

class FetchByIdNotFound extends FetchByIdResult {
  const FetchByIdNotFound();
}

class FetchByIdAuthError extends FetchByIdResult {
  const FetchByIdAuthError(this.statusCode);
  final int statusCode;
}

class FetchByIdNetworkError extends FetchByIdResult {
  const FetchByIdNetworkError(this.message);
  final String message;
}
```

Update `fetchById` to return `FetchByIdResult`:

```dart
Future<FetchByIdResult> fetchById(String id) async {
  if (!isAdminConfigured || id.isEmpty) {
    return const FetchByIdNotFound();
  }
  try {
    final resp = await _dio.get<dynamic>(
      '$_baseUrl/api/news/${Uri.encodeComponent(id)}',
      options: _reqOptions(),
    );
    final code = resp.statusCode ?? 0;
    if (code == 404) return const FetchByIdNotFound();
    if (code == 401 || code == 403) return FetchByIdAuthError(code);
    if (code != 200) return FetchByIdNetworkError('HTTP $code');
    final body = resp.data;
    if (body is! Map<String, dynamic>) {
      return const FetchByIdNetworkError('Bad response shape');
    }
    if (body['success'] != true) return const FetchByIdNotFound();
    final data = body['data'];
    if (data is! Map<String, dynamic>) return const FetchByIdNotFound();
    return FetchByIdSuccess(NewsArticle.fromMap(data));
  } on DioException catch (e) {
    return FetchByIdNetworkError(e.message ?? e.type.name);
  } catch (e) {
    return FetchByIdNetworkError('$e');
  }
}
```

Backwards compat: if any other call site reads `fetchById` (none today — grep confirms only `news_provider.dart:196`), they'll need a minor update. Add a thin shim if needed.

#### B2. Update the provider to surface the typed result
**File:** `lib/data/providers/news_provider.dart:184-196`

```dart
final newsArticleFetchProvider =
    FutureProvider.autoDispose.family<FetchByIdResult, String>((ref, id) async {
  final cached = ref.watch(newsArticleByIdProvider(id));
  if (cached != null) return FetchByIdSuccess(cached);
  return ref.read(newsServiceProvider).fetchById(id);
});
```

#### B3. Make NewsDetailScreen branch on the typed result
**File:** `lib/features/news/screens/news_detail_screen.dart:52-67`

```dart
@override
Widget build(BuildContext context) {
  final cached = ref.watch(newsArticleByIdProvider(widget.articleId));
  final fastPath = cached ?? widget.initialArticle;
  if (fastPath != null) return _buildArticleScaffold(context, fastPath);

  final fetchAsync = ref.watch(newsArticleFetchProvider(widget.articleId));
  return fetchAsync.when(
    loading: _loadingScaffold,
    error: (e, _) => _retryScaffold('Couldn\'t load article: $e'),
    data: (result) => switch (result) {
      FetchByIdSuccess(:final article) => _buildArticleScaffold(context, article),
      FetchByIdNotFound() => _notFoundScaffold(),
      FetchByIdAuthError(:final statusCode) =>
        _retryScaffold('Sign-in expired (HTTP $statusCode). Pull to retry.'),
      FetchByIdNetworkError(:final message) =>
        _retryScaffold('Couldn\'t load article: $message'),
    },
  );
}

Widget _retryScaffold(String message) => Scaffold(
  appBar: AppBar(title: const Text('Article')),
  body: Center(
    child: Column(
      mainAxisSize: MainAxisSize.min,
      children: [
        const Icon(Icons.cloud_off_rounded, size: 48),
        const SizedBox(height: 12),
        Text(message, textAlign: TextAlign.center),
        const SizedBox(height: 16),
        FilledButton.icon(
          onPressed: () => ref.invalidate(
            newsArticleFetchProvider(widget.articleId),
          ),
          icon: const Icon(Icons.refresh_rounded),
          label: const Text('Try again'),
        ),
      ],
    ),
  ),
);
```

#### B4. Auto-retry once on auth error (covers any residual A1 race)
Inside `fetchById`, when we hit a 401, attempt one explicit token refresh + retry:

```dart
if (code == 401 || code == 403) {
  // Single retry — Dio's interceptor already auto-retries on 401, but
  // only via its cached force-refresh path. The first request may have
  // had no token at all. Try once more after one second.
  await Future.delayed(const Duration(seconds: 1));
  // recursive call w/ a guard parameter to prevent infinite loop
  return _fetchByIdRetry(id);
}
```
Or simpler: keep the auto-retry inside the existing AuthedDio interceptor — it already does forceRefresh on 401. The caller sees only the second result. So actually **no additional retry needed** if A1 lands; the auth error path is just a safety net.

### Phase C — News tab re-tap signal

#### C1. New Riverpod provider for "tab pulse"
**File:** `lib/data/providers/news_provider.dart` (append)

```dart
/// Pulses (increments) every time the user taps the News bottom-nav tab
/// while already on the News branch. UI listens to this and resets to top.
final newsTabPulseProvider = StateProvider<int>((ref) => 0);
```

#### C2. Convert `_MainShell` from StatelessWidget to ConsumerWidget
**File:** `lib/core/router/app_router.dart:71-123`

```dart
class _MainShell extends ConsumerWidget {
  const _MainShell({required this.navigationShell});
  final StatefulNavigationShell navigationShell;
  ...
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    return Scaffold(
      body: navigationShell,
      bottomNavigationBar: NavigationBar(
        selectedIndex: navigationShell.currentIndex,
        onDestinationSelected: (index) {
          final reTapped = index == navigationShell.currentIndex;
          navigationShell.goBranch(index, initialLocation: reTapped);
          // News branch is index 0 in the _tabs list.
          if (reTapped && index == 0) {
            ref.read(newsTabPulseProvider.notifier).state++;
          }
        },
        destinations: ...
      ),
    );
  }
}
```

#### C3. NewsScreen listens to the pulse and resets
**File:** `lib/features/news/screens/news_screen.dart`

```dart
@override
Widget build(BuildContext context) {
  // Existing ref.listen for top-of-feed prepend stays.
  ref.listen<NewsState>(newsProvider, ...);

  // New: tab re-tap → jump-to-top + refresh-if-stale.
  ref.listen<int>(newsTabPulseProvider, (prev, next) {
    if (prev == null || next <= prev) return;
    if (_pageController.hasClients) {
      _pageController.jumpToPage(0);
    }
    ref.read(newsProvider.notifier).markUnseenSeen();
    // ignore: unawaited_futures
    ref.read(newsProvider.notifier).scheduler.refreshIfStale();
  });
  ...
}
```

#### C4. Reset on first paint after returning from a NewsDetail (optional)
The pulse only fires for tab re-tap. If user reads an article → presses back → they land on NewsScreen at the same index they swiped to before opening the article. That's fine for "back from detail" semantics; we are NOT changing that behaviour.

## Risks and Mitigation

| Risk | Mitigation |
|---|---|
| `getValidToken` hang blocks every cold start | 4-second `.timeout(...)` with silent fallback. Even at 4 s, splash content (cached articles) is already on screen. |
| Tab-pulse provider triggers spurious resets if Riverpod replays state on hot-restart | Pulse listener guards with `prev != null && next > prev`. On first build `prev == null` so no-op. |
| `_MainShell` becoming `ConsumerWidget` breaks any tests that mount it raw | None in repo today (`grep _MainShell` shows only one ref). If added later, wrap in `ProviderScope` per Riverpod test conventions. |
| Sealed class adoption ripples through call sites | Only one call site exists (`news_provider.dart:196`). Plan covers it explicitly. |
| Auto-retry-on-401 in `fetchById` could mask a genuine ban | The `AuthedDio` interceptor already retries 401 once. Plan does NOT add a second retry layer in `fetchById` itself — the typed `FetchByIdAuthError` is shown to the user, who can press the Try Again button. |
| User's stored reading position is lost on tab re-tap | Intentional — that's the requested behaviour. Detail-screen back button still preserves position (this is unchanged). |
| Tab pulse fires every News-tab tap, not just from-other-tab → re-tap. Hot-keyboarding could DDoS the refresh | `refreshIfStale` enforces a 30-second floor; the in-flight guard in `PeriodicSyncScheduler._safeRefresh` drops overlap. Free protection. |
| FCM payload article id is wrong/truncated server-side (R1.3) — even with auth fixed, fetch still 404s | Plan surfaces this as `_notFoundScaffold()` honestly ("Article no longer available") — *correct* UX for a genuine 404, vs the previous "everything is 404." If telemetry shows lots of `FetchByIdNotFound` post-fix, that's the signal to look at the admin pipeline. |
| Cold-start where App Check is misconfigured (no debug token allowlisted) | `.timeout(4s)` continues without a token, the deep-link drains, NewsDetailScreen mounts, fetch returns `FetchByIdAuthError`, user sees the retry screen with a clear "Sign-in expired" message — much better than today's silent "no longer available." |

## Verification Plan

### For Problem 1
1. **Cold-start race scenario:** Force-quit app → tap a news notification on the lock-screen. Observe: app launches, splash → app shell → NewsDetailScreen with the article rendered. No "Article no longer available."
2. **Backgrounded scenario:** Open app → press home → wait > 1 min → tap a news notification. Same expectation.
3. **Foreground scenario:** Open app → keep News tab visible → publish a test article from admin → tap the in-app notification banner. Same expectation.
4. **Genuine 404:** With the app open, request a notification for an article id that's been deleted in admin → tap. Expect `_notFoundScaffold()` "Article no longer available" — correct.
5. **Auth genuinely expired:** Manually clear the JWT in SharedPreferences → tap notification → expect `FetchByIdAuthError` UI with Try Again button. Tapping retry should succeed once the token refreshes.

### For Problem 2
1. Open app → swipe to article #5 → tap Profile tab → tap News tab. Expect: PageView at index 0, latest article visible, freshness chip says "Updated <few> seconds ago".
2. Same flow but with cache fresh (< 30 s old) → expect jump-to-top with no extra network request (refreshIfStale skips).
3. Same flow but offline → expect jump-to-top + stale banner stays at "Couldn't refresh" subtle amber tone.
4. Tap News tab repeatedly while at index 0 → no flicker, no spurious network calls (refreshIfStale debounces).
