## Problem Statement

User wants three coupled changes:

1. **Strip the News top bar** — remove "The Daily" label, the "X of N" pagination, and the refresh button.
2. **Auto-fetch news every 2 minutes** while the app is foregrounded.
3. **Auto-fetch news on cold start and on resume** (already partly wired — needs the stale-threshold tightened).
4. **Same auto-fetch behavior for tracks (content)** — currently has cold-start refresh only, no scheduler, no resume hook.

Current state:
- `news_screen.dart:163-246` defines `_TopBar` with title + pagination + refresh button.
- `news_sync_scheduler.dart:16-21` runs **every 6 hours**, with a **6-hour stale threshold** for resume — so a quick app-switch within 6 h does nothing.
- `app.dart:39` calls `newsScheduler.refreshIfStale()` on resume (will become a no-op once interval is 2 min, because cache is never stale enough).
- `content_provider.dart` has NO scheduler — refreshes once at cold start (`app.dart:88`) and never again until app restart.

---

## Open Question (flagged for user)

**Tracks "auto-fetch every 2 min" — really?** Tracks contain learning content (cards, tracks, quizzes) which changes far less often than news (probably weekly, not every 2 minutes). Polling tracks every 2 min wastes:
- User battery (background timer fires while app foregrounded but tracks tab isn't visible)
- Mobile data (potentially large content manifest re-downloads)
- Admin server cycles (every active user pings every 2 min)

**Recommendation in this plan:**
- News: **2-minute interval** (matches user request — fast-moving content)
- Tracks: **30-minute interval** (still feels "auto", but server-friendly)
- Both: refresh on cold start + on resume, same as news

If you want literal 2 min for tracks too, change one constant in step B3 — flagged below.

## Technical Solution

### Approach 1 — Reuse `NewsSyncScheduler` (chosen)
The class is already generic — it just takes `refresh` and `lastSyncedAt` callbacks. Rename it to `PeriodicSyncScheduler` and instantiate once for news, once for content. No new abstraction needed; one rename + two call sites.

### Approach 2 — Add a separate ContentSyncScheduler (rejected)
Duplicate code. Worse.

### Approach 3 — Use a single global scheduler driving both (rejected)
Couples news and content lifecycles together. Now if tracks fails, news retry timing is muddled. Worse.

### Lifecycle handling

Two events drive a sync:
1. **Cold start** — already wired in `app.dart:88, 94` for both. Keep.
2. **Resume from background** — `app.dart:37-40` only handles news currently. Extend to also kick content. For news, drop the stale threshold so a 2-minute resume always pulls fresh.
3. **Periodic timer** — `Timer.periodic` keeps firing even when app is backgrounded (it just won't have CPU until resume). Debounce in `_safeRefresh` to drop overlapping calls if a previous fetch is still in flight.

`Timer.periodic` does not pause itself when the app is backgrounded — but Android pauses the Dart isolate, so timers naturally don't fire. On resume the missed ticks fire late as a burst. The right pattern is: stop the timer in `paused`, restart in `resumed`. We do this in step C2.

### Top-bar removal

The `_TopBar` widget (lines 163-246) becomes dead code. Delete the class and its invocation at line 116-121. The category rail and feed body remain. Result: the news screen starts with the category rail at the top, beneath the system status bar. The pagination indicator was the only affordance to know "story 3 of 10" — gone per request. Refresh button was the only manual escape if auto-refresh hangs — gone per request, but pull-to-refresh on the empty state already exists at line 482; we'll preserve that as the safety net.

```dart

// After
class PeriodicSyncScheduler {
  PeriodicSyncScheduler({
    required this.label,                // e.g. "news", "content" — for debug logs
    required Future<bool> Function() refresh,
    required DateTime? Function() lastSyncedAt,
    required Duration interval,
    required Duration staleThreshold,
  })  : _refresh = refresh,
        _lastSyncedAt = lastSyncedAt,
        _interval = interval,
        _staleThreshold = staleThreshold;

  final String label;
  // ... rest unchanged
}
```

#### B2. Add reentrancy guard
- **File:** `lib/data/remote/periodic_sync_scheduler.dart`
- Guard against overlapping fetches if a previous one is still in flight (slow network + 2-min interval = real risk).

```dart
bool _inFlight = false;

Future<void> _safeRefresh(String source) async {
  if (_inFlight) {
    debugPrint('PeriodicSyncScheduler[$label]: $source skipped (in-flight)');
    return;
  }
  _inFlight = true;
  try {
    await _refresh();
  } catch (e) {
    debugPrint('PeriodicSyncScheduler[$label]: $source threw $e');
  } finally {
    _inFlight = false;
  }
}
```

#### B3. Tighten news interval + staleThreshold
- **File:** `lib/data/providers/news_provider.dart:63-69`
- Pass explicit values:

```dart
_scheduler = PeriodicSyncScheduler(
  label: 'news',
  refresh: () async {
    await refresh();
    return state.lastError == null;
  },
  lastSyncedAt: () => state.lastSyncedAt,
  interval: const Duration(minutes: 2),
  staleThreshold: const Duration(seconds: 30),  // resume always refreshes
);
```

The 30 s `staleThreshold` means any background→foreground switch where the cache is older than 30 s triggers a refresh. Tighter than that risks double-fetching when periodic and resume race (because resume fires _then_ the periodic timer immediately fires).

#### B4. Add a scheduler to `ContentNotifier`
- **File:** `lib/data/providers/content_provider.dart`
- Mirror the news pattern. Pick a longer interval (see Open Question above):

```dart
class ContentNotifier extends StateNotifier<ContentState> {
  ContentNotifier(this._service)
      : super(ContentState(...)) {
    _scheduler = PeriodicSyncScheduler(
      label: 'content',
      refresh: () async {
        await refresh();
        return _service.lastError == null;
      },
      lastSyncedAt: () => _service.lastFetchedAt,
      interval: const Duration(minutes: 30),     // ← change to 2 if user insists
      staleThreshold: const Duration(minutes: 1),
    );
  }

  late final PeriodicSyncScheduler _scheduler;
  PeriodicSyncScheduler get scheduler => _scheduler;

  @override
  void dispose() {
    _scheduler.stop();
    super.dispose();
  }
}
```

The `lastFetchedAt` accessor needs to exist on `ContentService`. Check:
- If `lastFetchedAt` is already set inside `_syncFromService` (line 87), it's there.
- If not, add it: assign `service.lastFetchedAt = DateTime.now()` after a successful network refresh.

### Phase C — Lifecycle wiring in `app.dart`

#### C1. Start the content scheduler at boot
- **File:** `lib/app.dart` after the existing `contentProvider.notifier.refresh()` call at line 88
- Add:

```dart
final contentNotifier = ref.read(contentProvider.notifier);
// ignore: unawaited_futures

```

#### C2. Stop schedulers in `paused`, restart in `resumed`
- **File:** `lib/app.dart:25-41`
- Currently `paused` only flushes telemetry; `resumed` only kicks news. Extend:

```dart
@override
void didChangeAppLifecycleState(AppLifecycleState state) {
  super.didChangeAppLifecycleState(state);

  if (state == AppLifecycleState.paused ||
      state == AppLifecycleState.inactive) {
    // ignore: unawaited_futures
    ref.read(telemetryServiceProvider).flush(force: true);
    // Stop foreground timers so they don't burn cycles when we resume.
    ref.read(newsProvider.notifier).scheduler.stop();
    ref.read(contentProvider.notifier).scheduler.stop();
  }

  if (state == AppLifecycleState.resumed) {
    final news = ref.read(newsProvider.notifier);
    final content = ref.read(contentProvider.notifier);
    // Pull anything we missed while backgrounded, then resume the timers.
    // ignore: unawaited_futures
    news.scheduler.refreshIfStale();
    // ignore: unawaited_futures
    content.scheduler.refreshIfStale();
    news.scheduler.start();
    content.scheduler.start();
  }
}
```

The `start()` call is idempotent in our scheduler (`_timer?.cancel()` then re-create), so double-firing it is safe.

#### C3. Verify `dispose()` cleans up
- **File:** `lib/app.dart:43-47`
- Already cancels the lifecycle observer. The schedulers are owned by the notifiers — Riverpod auto-disposes them via `dispose()` overrides we added in B4. No change needed.

## Risks and Mitigation

| Risk | Mitigation |
|---|---|
| **Battery drain** from 2-min polling | Stop timer on `paused` (step C2). Reentrancy guard prevents overlapping fetches on slow networks. |
| **Admin server load** — every active user pings every 2 min | Already protected by HTTP cache headers + idempotent GET. Worst case: re-evaluate interval per usage data. Flag to bump to 5 min if telemetry shows admin hot. |
| **Removing pagination removes user awareness** of feed length | Trade-off accepted per user request. Future option: thin progress dots overlaid on the right edge of cards. |
| **Removing refresh button removes manual escape** if auto-refresh stalls | Pull-to-refresh on the empty-state `RefreshIndicator` (line 482) still exists — that's the fallback. May want to add pull-to-refresh on populated state too (currently swipe goes to next article, not refresh). Out of scope for this plan. |
| **`AppLifecycleState.resumed` fires twice** on some Android variants when returning from a permission dialog | `_safeRefresh` reentrancy guard absorbs the duplicate. `start()` is idempotent. |
| **Content refresh every 30 min downloads a large manifest** | Server should send `Last-Modified` / `ETag` and respect 304 responses. If not, the wasted bandwidth is real — flag for backend follow-up. |
| **Periodic timer fires immediately after `start()`?** | No — `Timer.periodic` waits one full interval before the first tick. Cold-start fetch is separate at `app.dart:88,94`. So users see the first periodic refresh at +2 min, not at 0 min. That's fine. |
| **Stop scheduler on `inactive` is too aggressive** — `inactive` fires on transient interruptions (incoming call, control center swipe) | Dropping `inactive` from the stop trigger and only stopping on `paused` would be safer, but `paused` is consistently fired before background, so it's enough. Keep both for symmetry with the existing telemetry flush logic. |
| **News cache age + 30 s staleThreshold races with periodic fire** | If user backgrounds at T=0, returns at T=119 s, `refreshIfStale` fires, periodic also fires at T=120 s, the in-flight guard skips one. ✓ |
